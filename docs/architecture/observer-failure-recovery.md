# Observer: локальный отказ и восстановление

Изменение не отменяет проверку цели, непрерывности событий и освобождения ввода.
Обычная смена фокуса инвалидирует старое наблюдение; это не неисправность процесса.

## Границы отказа

Native передаёт отказ observer отдельным `event` envelope:
`runtimeEpoch`, `loginSessionId`, `nativeGeneration`, `observerInstanceRef`, `gapReason`.
Это сообщение не выдаёт себя за GUI-событие и не занимает его sequence.
Command loop отправляет его один раз для instance и запрашивает отмену активного job.
Helper не завершается из-за этого сообщения: transport, status, cleanup и независимое
чтение остаются доступными. Ошибки самого транспорта по-прежнему терминальны.

Adapter завершает только reader событий. Hub сообщает gap подписчикам, Guard
инвалидирует tickets. Host снимает observer/view capabilities, но не накладывает
глобальный admission seal поверх исправных независимых методов.

## Восстановление

Новый явный `observe` либо host `ready()` может подготовить observer снова.
Пока есть active Core operation, новый prepare не запускается. Старые Guard/Hub
закрываются; exact Native stop должен быть подтверждён до следующего prepare.
Неизвестный исход prepare запрещает новую попытку на том же host: отсутствие
ответа не считается отсутствием созданного instance.

Завершённая попытка подготовки не кешируется навсегда. При успешной замене
создаются новый Guard и новый набор tickets; старые tickets не восстанавливаются.
Protected methods регистрируются один раз, а их видимость определяется capabilities.
`system_health` остаётся пассивным и не запускает подготовку или повтор действий.

Никакие mutation не повторяются. Recovery/quarantine незавершённых операций и
проверки Core перед открытием admission сохранены.

## Согласование событий

Один Hub обслуживает конкурентные coverage callers одним Native RPC. Отмена одного
caller не отменяет ожидание других. Весь RPC и догоняющая доставка используют один
control deadline. Отставание доставки до deadline — ожидание, после deadline —
неудача данного запроса, а не выдуманный gap.

Snapshot проверяется относительно sequence в момент отправки запроса. Уже пришедшие
более новые события не делают старый корректный snapshot регрессом. Cursor старой
отметки сверяется с сохранённой историей; неизвестный или несовпадающий cursor не
принимается на веру. Настоящие пропуски и смена identity остаются fail-closed.

Guard ожидает достижение отметки, а не равенство с уже пройденным значением. В proof
входит фактически обработанный watermark. Более новые релевантные события всё равно
инвалидируют ticket. Диагностика coverage содержит конкретные нарушенные условия и
исходный reason.

## Проверки

Regression fixtures проверяют snapshot/PUSH в обоих порядках, timeout с последующим
догонянием, общий RPC и раздельную отмену, настоящее повреждение cursor, восстановление
после clean prepare/coverage failure, запрет retry при unknown cleanup и отказ observer
при idle без завершения helper. Native command-loop fixtures не отправляют системный ввод.

Это локальное исправление lifecycle, не замена всей архитектуры. TTL handles,
таймеры ротации, heartbeat активного ввода и протокол capture здесь не удаляются.
