# Стабильный proxy и изменяемый Runtime

Автор: zavx0z. 21 сентября 2026.

## Граница

`ChatGPT → zavx0z proxy → authenticated UDS → Runtime agent_request → существующие методы / tools`

Proxy не содержит списков компьютерных действий, видов browser requests, видов
шагов конвейера, реализации vendor/tools или производных текстов их контрактов.
Разделы `computer` и `tools` используют одно подключение и одну клиентскую lineage
Runtime. Knowledge Base сохраняет свой уже динамический HTTP-каталог; viewer
остаётся представлением беседы в proxy, а не исполнителем на Mac.

Стабильная оболочка `agent_request` принимает `node`, необязательные `action` и
`input`, и необязательный `allowedActions`, который только сужает серверный профиль.
Она возвращает `payload`, `frameRefs`, `isError`. Proxy разворачивает оболочку,
сохраняет структурированный результат/ошибку, загружает кадры по прежнему UDS и
публикует их в том же viewer. Отдельный MCP entry point не добавлен.

## Допуск не заменён подсказками модели

MethodRegistry хранит private-флаг `agent`, установленный доверенной регистрацией
метода. Существующий набор перенесён из proxy в `agent-actions.ts`; новый метод
может явно установить `agent: true` в своём определении. Неизвестный метод без
такого допуска не виден агенту, даже когда public в полном UDS-каталоге и имеет
`readOnlyHint: true`. `internal` не раскрывается через agent, `agent: false` не
переопределяется клиентом. Сама оболочка не может рекурсивно вызвать себя.

`agent-browser-policy.ts` сохраняет запрет навигации, создания/закрытия вкладок,
произвольного evaluate и CDP-команд. `agent-pipeline-policy.ts` проверяет весь план
и разрешения дочерних действий до первого шага. Эти ограничения принадлежат
Runtime, не дублируются в proxy. Полные схемы, epoch, target ownership, reservations,
Native admission, receipts и cleanup остаются в прежних исполнителях.

Наличие операции в каталоге не является пользовательским поручением на её вызов.
GET ресурса сайта также не доказывает отсутствие прикладных побочных эффектов:
агент выбирает только необходимые источники в рамках поручения, а не произвольные
URL. Это граница реализации, не универсальная гарантия безопасности любого сайта.

Proxy копирует вход до первого await. Runtime повторно валидирует запрос и
проверяет доступность перед исполнением. Оболочка не удлиняет тайм-аут дочернего
метода: например, конвейер сохраняет 30 секунд. После timeout/unknown нет
автоматического повтора; эффекты выясняются по дочерним операциям и наблюдению.
Для ответа метода wire учитывает один внешний объект `data/frameRefs`: глубина
собственно data по-прежнему не больше 32, что проверяют и Runtime, и клиент;
транспортный объект вместе с data может иметь глубину 33. Лимиты входа и других
ответов не увеличены. Эта граница проверена полным контрактом browser operation.
Файловые операции идут через прежний dispatch vendor/tools, с проверкой машины,
expectedHash, отменой и сохранением ошибок. При sealed admission gateway не
исполняет tools actions; справка не превращается в действие.

## Что обновляется дальше

Новый browser read, вид шага, компьютерный метод или файловый инструмент меняет
Runtime и его тесты/контракты. Proxy узнаёт актуальный каталог при обращении и
пересборки из-за этих изменений не требует. Производная упаковка vendor/tools
генерируется `scripts/tools-metadata.ts` в `runtime/src/tools-metadata.ts`.

Изменение транспортной оболочки, аутентификации, wire-протокола или самого viewer
всё ещё может требовать обновления proxy. Обещания «proxy больше никогда не
обновляется» нет. Импорты transport сделаны точечными: backend/feature barrel не
втягивается в сборку proxy.

## Переход установленной версии

Первый переход требует Runtime, поддерживающий `agent_request`, затем новую сборку
proxy. Старый proxy может работать с прежними публичными Runtime-методами на время
перехода. Новый proxy со старым Runtime отказывает без direct-method, локального
filesystem или иного fallback. Runtime и proxy устанавливаются штатными CLI;
установка proxy останавливает tunnel session и должна иметь действительно
независимый внешний запуск и путь возврата. Наличие TTY само по себе этого не
доказывает. Установку и её live-результат подтверждают manifest/receipts/health,
а не commit или этот документ.

## Основа сбора данных

`read-dom` и `read-resource` передают байтовые части с offsetBytes,
nextOffsetBytes, totalBytes, snapshotSha256, truncated. Для продолжения одного
снимка потребитель передаёт expectedSnapshotSha256; при изменении содержимого
части не склеиваются. UTF-8 границы и BOM сохраняются. `read-resource` ограничен
HTTP(S) тем же origin, проверенным на стороне host и непосредственно в контексте
страницы, фиксированным GET, credentials=include, mode=same-origin,
redirect=error. В теле нет передаваемого агентом JavaScript. Внешний chunk не
больше 1 MiB, читаемый ресурс ограничен 16 MiB. Сервер повторно получает ресурс
для следующей части и проверяет hash; это не хранилище неизменяемого снимка.

Чтение DOM не доказывает наличие всей истории в отрисованной странице. Ответ
HTTP, его код, обрезка и полнота прикладного набора требуют отдельной проверки.
Реестр чатов, сообщения, вложения и импорт KB не объявляются собранными только
потому, что транспорт чтения прошёл изолированные тесты.

## Проверки

`mcp/tests/proxy-runtime-boundary.test.ts` проверяет состав собранного proxy,
появление новой server-opt-in операции без смены proxy, отказ скрытых методов,
старого Runtime и локального filesystem fallback. MCP-интеграционные тесты
проверяют тот же viewer, frame refs, ошибки, позднюю регистрацию и отсутствие
повторного исполнения. `runtime/tests/agent-service.test.ts` проверяет запрет
browser/pipeline до дочернего вызова, narrow permissions и дедлайны.
`chrome/tests/read-chunks-script.spec.ts` исполняет фиксированное выражение чтения
в изолированной fake-page среде, проверяет смену origin и точное восстановление
Unicode/BOM. Это не испытание настоящего Chrome или реального сайта.
