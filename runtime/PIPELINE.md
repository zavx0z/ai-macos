# Локальный конвейер Runtime — первый объём

`run_pipeline` — конечная последовательность существующих методов Runtime.
Это не JavaScript evaluator, не очередь фоновых задач и не отдельный Runtime.
Один внешний вызов выполняет ожидания и действия локально и возвращает общий
результат, номера дочерних операций и, когда захват доступен, один финальный кадр.

## Реализовано

- Один точно выбранный **уже показанный и сфокусированный native window**,
  его `targetId`, ожидаемый `expectedBundleId`, текущий `runtimeEpoch` и свой
  `clientRequestId`. Окно или приложение не выбираются по принципу «первое».
- `wait`, `press` по найденному AX-элементу и `keys` — последовательность
  существующего `press_shortcut` с нулевой искусственной задержкой.
- Шаги Chrome: `chrome-connect` возвращает pending внутри конвейера;
  `chrome-consent` проверяет native-dialog и выполняет AXPress;
  `chrome-wait` ждёт **эту же операцию**; `chrome-read` читает точную вкладку;
  `chrome-disconnect` отключает своё соединение и проверяет результат.
- Ожидание повторяет только чтение, с отменяемой паузой 80 ms между отрицательными
  наблюдениями. При matched действие продолжается сразу. Это ограниченный опрос,
  не обещание event-driven распознавания.
- Бюджет конвейера 30 секунд, подчинён более раннему deadline вызова. Прежнее
  ожидание согласия Chrome 25 секунд **не изменено**.

Ввод проходит `check_input → fresh observe → действие` через прежние публичные
методы и их private view/lineage/Native admission. Изображение не создаёт
полномочий на ввод. `keys` проверяет фокус **окна**, а не конкретного текстового
поля. Автоматическая клавиатурная активация запроса разрешения не включена:
для неё используется точный AXPress, без угадывания количества Tab/Enter.
Смена окна внутри одного конвейера и `type_text` с доказанным фокусом поля
пока не входят в первый объём.

## Относительные условия

Каждая контрольная точка содержит `anchors`, `select` и `origin`.
Ориентиры задаются в порядке зависимостей; `within` ссылается на предшествующий
ориентир либо `$window`. Поиск требует уникального результата. Пример:

```json
{
  "origin": "native-dialog",
  "select": "allow",
  "anchors": [
    {
      "name": "dialog",
      "selector": {
        "subrole": "AXApplicationAlertDialog",
        "text": "Разрешить удалённую отладку?"
      },
      "region": {
        "x": 0.2, "y": 0.2, "width": 0.6, "height": 0.6,
        "tolerance": 0.05
      }
    },
    {
      "name": "cancel", "within": "dialog",
      "selector": { "role": "AXButton", "text": "Отмена" }
    },
    {
      "name": "allow", "within": "dialog", "rightOf": "cancel",
      "selector": { "role": "AXButton", "text": "Разрешить" }
    }
  ]
}
```

Это пример описания, **не подтверждённый selector живого диалога Chrome**.
Реальные role/subrole/text необходимо получить наблюдением перед развёртыванием.

Координаты AX — глобальные macOS points. Относительная область пересчитывается
из текущих границ окна/контейнера. Она ограничивает поиск центра кандидата;
сама кнопка должна целиком находиться в своём контейнере. `rightOf` и `below`
сравнивают реальные границы ориентиров. Приближённого клика нет: `press`
использует свежий `elementId` и AXPress. Пиксели preview в расчёте не участвуют.
Ориентиры заново вычисляются по **одному** полному наблюдению на каждой точке;
старые elementId не служат ссылками между кадрами.

Результаты детектора: `matched`, `not-found`, `ambiguous`, `unavailable`.
Повторяется только `not-found`; неоднозначность, неполный AX, отсутствие
геометрии у возможного кандидата или неверная принадлежность останавливают ввод.
Текст сравнивается по отдельным полям, с NFC и нормализацией пробелов;
по умолчанию exact, contains требуется указать явно. Нечёткое «похожее слово»
не используется для разрешения действий.

## Разрешение Chrome

Нужны одновременно незавершённая операция connect этого конвейера, точное
Chrome-окно и найденный AX-диалог **вне AXWebArea/AXHTMLContent**. Изображение
диалога или web-имитация не проходят этот критерий. Неполная родительская
цепочка также не принимается. Пока connect pending, generic keys/press запрещены;
разрешён только отдельный guarded `chrome-consent`. После завершения connect
требуются новая transport generation и активная reservation своей lineage.

Проверки не доказывают связь видимого диалога с конкретным внешним CDP-клиентом
при конкурирующих запросах вне Runtime. Живая проверка этой ассоциации и
фактической структуры диалога ещё не проведена. Изолированные фикстуры не
доказывают работоспособность или время сценария на настоящем Chrome.

Первая `chrome-read` выбирает уникальную вкладку по точному URL и закрепляет её
полный ref. Последующие чтения должны относиться к тому же ref; вкладка с тем же
URL, но новым targetId, не подставляется автоматически. В отчёте возвращаются
метаданные и SHA-256 прочитанного содержимого, не полный DOM. Чтение ограничено
32 KiB; `truncated` сохраняется.

## Итог, отмена и повтор

`final.condition` проверяется повторно по тому же combined AX+image observation,
которое возвращается как конечный кадр. Отказ такого наблюдения не выдаётся за
успех. Для `final.chromeDisconnected` результат доказывают операция disconnect
и свежий browser inventory; недоступность картинки отдельно отражается в отчёте.

`dispatched` у шага ввода означает доставку, а не эффект приложения. `verified`
у конвейера означает, что прошли явно заданные финальные условия. Частичное или
неизвестное выполнение останавливает зависимые действия. Автоматического
повтора нажатий и отката интерфейса нет.

При отказе конвейер отменяет только свой ещё выполняющийся connect. Для ранее
подтверждённой своей active reservation он может один раз исполнить уже
предусмотренный планом disconnect, в пределах исходного бюджета. Unknown
transport не превращается в «очищен»: `connectionCleanup=unconfirmed` сохраняет
необходимость прочитать точный receipt/recovery. Cleanup operations перечислены
отдельно от основного пути.

Небольшой ограниченный cache результатов предотвращает повтор mutations при
идентичном запросе в той же runtime/client lineage. Изменённый payload с прежним
ID отклоняется. Cache не вытесняется молча ради нового исполнения; после
перезапуска старый runtimeEpoch отклоняется. Это не durable журнал конвейеров:
источником истины для эффектов остаются дочерние Core receipts. После потери
ответа сначала читать receipts, не отправлять новый ID для повторения плана.

## Границы подключения

Сейчас условия исполняются по системному AX. **OpenCV/OCR backend не реализован
и не установлен.** На графическом элементе без достаточного AX конвейер
возвращает unavailable/not-found, а не имитирует распознавание. Архитектура
условий не требует указания OCR-библиотеки снаружи; реализация другого
источника наблюдений и проверка provenance остаются отдельным следующим объёмом.

`run_pipeline` зарегистрирован в исходниках Runtime. В исходниках proxy имя
добавлено в `computerActions`; `mcp/src/pipeline-policy.ts` проверяет весь план
до подключения и отправки в Runtime. Составной вызов не расширяет явный
`allowedActions` клиента: нужны разрешения на вложенный ввод, наблюдение,
Chrome-операции, чтение receipt и reservation. Неизвестные виды шагов и режимы
чтения запрещены. Виды CDP-операций проверяет прежняя `browser-policy.ts`.
Полную схему, последовательность согласия, target/lineage, admission и cleanup
по-прежнему проверяет Runtime; proxy не создаёт второй исполнитель или схему AX.
Проверенный план копируется до первого await, чтобы входной объект нельзя было
подменить во время подключения. Отдельная операция MCP не добавляется:
метод раскрывается внутри существующего `zavx0z` только когда доступен в Runtime.

Это изменение исходников, **не установка**. Рабочие proxy/tunnel и Runtime
не обновлялись, commit и push не выполнялись. Перед живым запуском остаются
проверки политики и штатное согласованное развёртывание с независимым путём
возврата. Отсутствие имени в установленном каталоге не обходится другой тулой.
